# CVNS R-06.2 小说写作 Skill 设计书（v1.7.0）

> **文档性质**：这份设计书是当前版本的设计提案与工作记录，**不保证正确**，也不是文学质量、商业效果或“自动写完整本小说”的承诺。生成高质量小说仍然需要讨论、对照实验、人工审读和反复修正。
>
> **归档范围**：本目录只包含设计文档、提示词、工具、测试与问题记录；**不包含任何测试小说正文、样章、修订候选或样本输出**。历史测试的数据流分析报告不含小说正文，见 `case_studies/` 与 `PROBLEMS.md`。

## 0. 摘要

CVNS R-06.2 是一个“微任务变量线”小说写作流程的提示词与工程规范。它不试图用一段超长提示词一次性生成整本书，而是把写作拆成许多可独立执行、可审计、可批准的自然任务：

- 一条 `entity × dimension` 的完整变量线作为 canon 状态；
- 一次模型调用只执行一个任务，使用独立会话、最小输入包和独立输出；
- 生成、审计、修订、批准、冻结分离；
- 未解释清楚的冲突不直接交给 Writer；
- 资产按 SETUP / REVEAL / PAYOFF 阶段部署，事件去重并绑定唯一状态节点；
- 通过确定性工具和测试验证结构、预算、契约和回归。

这份设计的价值在于**可追踪与可讨论**，不在于宣称已经解决了“怎样写出高质量小说”。

## 1. 问题定义

| 问题 | 常见表现 | 本设计的回应 |
|---|---|---|
| 长上下文漂移 | 章节越写越长，人物/世界设定前后不一致 | 用变量线保存 entity × dimension 的完整时间轨迹，按任务投影最小输入包 |
| 事件同质化 | 多个资产都被机械地变成相似事件 | P12B 资产组合筛选、P13B 阶段化事件机会、P14C0 去重与唯一节点归属 |
| 冲突被当作事实 | 未解决的矛盾直接进入正文 | P09/P10 分类，P11A/P11B 先探索解释，批准后才资源化 |
| 生成与审计混在一起 | 一次调用既写正文又自我验收 | 一次任务一次调用，P18 Writer 与 P19 审计分离 |
| 过程不可追踪 | 不知道哪份输出被下游使用 | 输出契约、生命周期注册表、消费追踪、preflight |
| 流程成本不清 | 重复调用、输入包膨胀 | 输入包去重、预算/重复子树审计、可避免调用记录 |

## 2. 目标与非目标

### 目标

1. 把长篇写作流程拆成可独立执行、可审计的微任务。
2. 用变量线而不是章节摘要保存 canon 状态。
3. 把“生成、审计、修订、批准、冻结”分开。
4. 用 schema、输出契约和确定性工具验证结构，而不是让模型自证。
5. 给宿主调度器留下清晰的权限、审批、冻结和索引接口。
6. 把已知问题和不保证事项写清楚，方便别人批评和接手。

### 非目标

- 不是“一句提示词自动写完一本小说”。
- 不是原 R-06.2 Python 工程的源码替代。
- 不是文学质量、商业成功或模型能力的证明。
- 不是某个模型/供应商的官方结论。
- 不是对所有题材都适用的固定模板。

## 3. 总体架构

```text
[Canon / 变量线]
      │
      ▼
[TASK_REGISTRY / 提示词] ──► [输出契约 / Schema] ──► [宿主审批 / 冻结]
      │                                                     │
      └──────────────► [确定性工具 / 测试] ◄────────────────┘
                              │
                              ▼
                     [下游任务 / 证据 / 问题记录]
```

| 层 | 内容 | 是否随包提供 |
|---|---|---|
| Canon / 状态层 | BASE/DERIVED 变量线、WorldConstants、StoryAsset、Event | 规范与 schema 提供；实际数据不随包 |
| 任务层 | `TASK_REGISTRY.csv`、84 个提示词文件、任务输入/输出范围 | 是 |
| 契约层 | `schemas/`、`schemas/output_contracts/`、validators | 是 |
| 宿主层 | 独立会话、输入包拼接、权限、审批、冻结、索引激活 | **否，需要宿主实现** |
| 工具层 | preflight、校验器、物化器、索引事务、冲突解释工具 | 是（核心 27 个工具，含 real_novel_test / writer_length_contract 两个测试/契约工具；另有 18 个样章专用工具因依赖未上传测试证据而移除） |
| 证据层 | tests、case_studies、regression、问题记录 | 是（不含测试小说正文） |

## 4. 数据模型

| 对象 | 作用 | 关键约束 |
|---|---|---|
| BASE 线 | 一个 entity × dimension 的完整时间轨迹 | 一次调用一条完整线；不按章节/字段切碎 |
| DERIVED 线 | 由 BASE/规则推导出的状态 | 必须能追溯来源和推导规则 |
| WorldConstants | 世界规则、机制、等级、战斗规则 | 需要 P01B/P01E/P01F + P21A/宿主批准 |
| StoryAsset | 可被 setup/reveal/payoff 的故事资产 | 按阶段绑定目标章，阶段级唯一归属 |
| Event | 有行动、决策、时空窗口和结果变化的事件 | P13C 决策计划不等于 Event 实际结果 |
| Conflict | 张力、互斥、确认因果、待证据、无实质关系 | 未解释/未批准的互斥不得资产化 |
| DecisionProfile | P05E 稳定决策倾向 sidecar | 不是第 12 条 BASE 线；临时状态仍由既有维度承载 |
| Lifecycle | 产物版本、冻结、激活、失效 | 冻结成果不得原位修改 |

### 4.1 变量线为什么是完整时间轨迹

章节摘要会丢掉“什么时候知道/不知道”“什么时候状态改变”这类信息。变量线按 entity × dimension 记录时间轨迹，P09 扫描实体对时读取完整已签约线，P13B/P13C 再按事件时间窗口投影。代价是输入包可能很大，因此需要最小输入包、去重和预算。

### 4.2 生成与审计分离

P18 Writer 只负责写；P19 系列按 POV、知识边界、机制、物品、身体、位置、因果、钩子、声音、时间、主题等维度分别审计。审计不能修改正文；修订必须新版本。

## 5. 任务与提示词

- `TASK_REGISTRY.csv`：83 个任务行，描述 task_id、prompt_file、output_contract、call_unit、read_scope、write_scope、predecessor、validators。
- `prompts/`：84 个提示词文件（含 BASE 维度提示词）；每个提示词只保留唯一目标、最小输入、限制和单一输出。
- 预算：最长 3000 字符、最多 15 项限制；基础维度另有更严约束。
- 提示词中不出现 `predecessor`、`validators`、调度命令或下游验收指令；这些只留在注册表和宿主说明。
- 生成、审计、修复、批准分开；一个任务不越权做下游验收。

任务分组（详见 `TASK_REGISTRY.csv`）：

| 阶段 | 任务 |
|---|---|
| 项目/世界 | P00、P01A–P01F、P02A–P02C、P03A–P03B |
| 实体/人物 | P04A–P04C、P05A–P05F |
| 变量线/审计 | P06、P07A–P07C |
| 冲突/解释 | P08、P09、P10、P11A、P11B、P11 |
| 资产/事件 | P12、P12B、P13、P13B、P13C、P14A、P14B、P14C0、P14C |
| 章节/Writer | P15A、P15B、P16A–P16C、P17A–P17C、P18、P18D |
| 审计/修订 | P19A1–P19I、P20、P21A、P21B、P22–P26 |

## 6. 执行流程

1. **项目契约**：P00 提取用户明确给出的项目信息；缺失项标 UNSPECIFIED。
2. **世界与主题**：P01A–P01F 建立世界事实、机制、修炼/战斗提案；P02/P03 建立主题与锚点。
3. **实体与人物**：P04/P05 建立实体候选、必要性、功能、声音卡、决策倾向。
4. **变量线**：P06 全局表达矩阵；P07 审计；BASE 线按 entity × dimension 一次调用。
5. **冲突**：P08 节奏意图、P09 实体对扫描、P10 分类；P11A/P11B 先探索解释，未批准不资源化。
6. **资产与事件**：P12B 组合筛选、P13B 阶段化事件机会、P13C 决策计划、P14A 转 Event、P14B 可行性、P14C0 去重。
7. **章节与 Writer**：P15 章节 beat、P16 生命周期、P17 前置检查；P17C 未 READY 时 P18 必须阻断，诊断只能走 P18D。
8. **审计与修订**：P19 系列审计、P20 影响分析、P21 规则修订、P22–P25 后续完善；P26 只做长篇压力测试 sidecar。
9. **批准与冻结**：宿主批准、物化新版本、索引激活、旧审读失效；旧冻结包不覆盖。

关键工具：

- `tools/timing_approval_gate.py`：时间来源、语义审读与宿主批准证据校验。

## 9. 设计取舍

1. **一次任务一次调用**：降低注意力稀释、便于审计；代价是调用次数和编排复杂度增加。
2. **变量线而非章节摘要**：保留时间轨迹和知识边界；代价是输入包更大，需要投影/去重。
3. **生成/审计/批准分离**：避免自证；代价是更多调用和人工审批。
4. **冲突先解释再资源化**：避免把未解决矛盾写成事实；代价是流程更长，不是每个冲突都能解释。
5. **sidecar 机制**：P05E/P13C/P26 用 sidecar 保存扩展语义，不轻易改核心 schema；代价是宿主需要理解多个工件。
6. **确定性工具只做结构校验**：不把“结构通过”伪装成“文学质量通过”；代价是仍需人工审读。
7. **宿主与 Skill 分离**：Skill 不假装拥有文件权限和会话隔离；代价是开箱即用性差。

## 10. 已知问题

完整列表见 `PROBLEMS.md`。最关键的几条：

- 宿主调度器未随包提供；没有宿主时无法完成冻结、权限、会话隔离和索引激活。
- 文学质量未被证明；静态测试只验证结构、预算、契约和回归。
- 历史实测样本很小，正式批准章节为 0；没有与简单长提示的对照基线。
- 输入包仍可能很大；150/200/300 KiB 是工程阈值，不是质量保证。
- 提示词预算（15 项 / 3000 字符）可能压缩复杂语义。
- 模型、tokenizer、费用和输出质量随 provider/model 变化。
- 测试小说、样章和修订候选**不在本归档中**；历史测试不能只靠本包复现。
- 18 个样章专用工具与 19 个样章专用测试已移除；`tools/real_novel_test.py` 与 `tools/writer_length_contract.py` 保留为测试/契约代码，但需要外部样章证据才能走完整路径。

## 11. 验证计划

### 已做的结构验证

- `python tools/validate_skill.py`：任务注册表、提示词、预算、输出契约的结构检查。
- `pytest -q` / `unittest discover`：契约、schema、生命周期、冲突解释、时间门禁、Writer 依赖等测试。
- 历史数据流分析：V1.4.1 的一次小规模记录（不含小说正文），见 `PROBLEMS.md` 与 `case_studies/`。

### 还需要做的质量验证

1. **对照实验**：同一大纲、同一模型、同一预算，比较本流程与“简单长提示 + 直接写作”基线。
2. **预注册指标**：canon 矛盾率、事件同质化比例、可避免调用数、总成本、人工审读评分、批准章节数、连续性错误。
3. **多题材/多规模**：至少两部不同题材、不同长度的小说，避免单样本结论。
4. **失败记录**：保留失败分支、被拒绝的解释、被延期的事件；不要只挑成功案例。
5. **可证伪条件**：若本流程在矛盾率/同质化/成本上没有可重复优势，或文学质量明显下降，应缩小主张或修正设计。

**本归档不包含测试小说正文**，因此上述质量实验需要在本地重新准备样本，并自行确认版权/隐私。

## 12. 这份设计不保证什么

- 不保证写出高质量小说，也不保证比简单提示更好。
- 不保证任何模型、供应商或 tokenizer 下的相同表现。
- 不保证节省成本；流程本身增加调用和编排开销。
- 不保证可自动写完整本小说；存储、状态、评估和人工审读仍是问题。
- 不保证设计书本身正确。它是一份可批评、可修正的工作假设。

## 14. 讨论方式

欢迎在 0-1 仓库的 Issues 中提出：

- 反例：某个任务在什么输入下会产出错误结构或不可用结果；
- 对照实验：与简单长提示、其他写作流程的比较；
- 设计批评：哪些约束是必要的，哪些是过度工程；
- 质量评估：怎样定义和测量“高质量小说”；
- 宿主实现：权限、会话、冻结、索引的具体实现。

设计书不是结论，而是讨论的起点。
