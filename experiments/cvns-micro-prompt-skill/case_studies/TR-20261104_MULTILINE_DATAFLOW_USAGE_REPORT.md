# TR-20261104-MULTILINE：数据消费、丢弃与输入包效率审查

## 1. 运行规模与统计口径

**口径更正**：本次 usage 有 74 个子代理会话，其中一条 P07C retry 未进入 call_log；因此 call_log 的 73 行不能代表全部会话。74 个 JSON 文件仍按文件清单统计（73 个模型输出 + 1 个 P19B 确定性 `NOT_APPLICABLE` 记录），不能用输出文件数推定会话数。

| 指标 | 数量/大小 | 说明 |
|---|---:|---|
| call_log 记录 | 73 | `call_log.csv` 行数；另有 1 次 P07C 重试未入日志 |
| 子代理会话 | 74 | 用户 usage 账单口径；不得与日志行数混用 |
| 输出 JSON | 74 | 73 份模型输出 + 1 份 P19B `NOT_APPLICABLE` 确定性记录 |
| 冻结副本 | 22 | 既有成果的版本副本，不是新增模型生成 |
| 输入包 | 73 | 合计 4,536,162 bytes，约 4.326 MiB |
| 输出 JSON 总量 | 1,088,387 bytes，约 1.04 MiB | 字节数不是 token 数 |
| 正式批准章节 | 0 | P17C 未达到 READY；P18 只有诊断草稿 |

本报告将“下游有精确 artifact/domain ID 引用”视为可追踪消费证据，而不把它夸大为模型语义上真正采用。引用链不证明模型在语义上完整理解了数据；没有引用也不自动等于浪费，审计、门禁、提案和终态判断本来就可能是末端成果。

## 2. 73份模型输出文件的保守分类

| 分类 | 数量 | 占模型输出 | 解释 |
|---|---:|---:|---|
| `EXACT_ARTIFACT_REFERENCE` | 20 | 27.4% | 下游输入包出现精确 artifact ID 引用 |
| `DOMAIN_REFERENCE_ONLY` | 40 | 54.8% | 下游出现领域对象/冲突/事件/资产 ID，不是精确 artifact ID |
| **有下游引用** | **60** | **82.2%** | 上两类之和；只是可追踪使用证据 |
| `TERMINAL_GATE_OR_AUDIT` | 5 | 6.8% | 终端审计/门禁，设计上不必进入 Writer |
| `TERMINAL_NO_ASSET_NEEDED` | 1 | 1.4% | P10 判定无实质冲突，正确终止，不应制造资产 |
| `PROPOSAL_ONLY_NOT_APPLIED` | 1 | 1.4% | P11 修复提案未获批准，保留为提案是正确行为 |

| `AVOIDABLE_NO_APPROVED_VOICE_CARD` | 1 | 1.4% | P19F 无批准 VoiceCard，正式声纹保真审计应在调用前 SKIP |
| `EMPTY_OUTPUT_SHOULD_HAVE_BEEN_SKIPPED` | 1 | 1.4% | P05C 无语言样本仍被调用，生成空 VoiceCard |
| `UNREFERENCED_REVIEW_REQUIRED` | 3 | 4.1% | 三份 P04B 对已在 EntityRegistry 的实体重复审查，未形成新增注册提交 |
| **合计** | **73** | **100%** | 每份模型输出只计入一类 |

### 结论：使用了多少、丢弃了多少？

- **60/73（82.2%）** 有下游精确产物或领域 ID 引用。
- 另有 **8/73（11.0%）** 是有合法终态价值的审计、门禁、无资产结论、未应用提案或被替代前的诊断版本。
- **5/73（6.8%）** 是明确可以避免的调用：3份已注册实体的 P04B 重复调用 + 1份没有语言样本的 P05C 空调用 + 1份没有批准 VoiceCard 仍执行 P19F。P19F 不应再单列为“部分诊断价值”来弱化其 preflight 可避免性。

以上引用率分母是 73 份模型输出文件；74 个输出 JSON 中的确定性 `NOT_APPLICABLE` 记录不进入模型输出分母。73 条 call_log 记录、74 个子代理会话、73 份模型输出文件为不同统计单位；1 次 P07C 重试未记入 call_log。

## 3. 分阶段：哪些产物被采用，哪些没有进入最终故事？

### 3.1 BASE 与审计

- 4条 BASE 变量线均被 P07 系列读取并审计；3条冻结，1条 ITEM 线保留 `DRAFT_WITH_KNOWN_GAP`。
- 15份 P07 审计输出都用于冻结、返修/重审或阻断决策。关系线 V1 的 P07C `REJECTED` 报告被用来修复输入白名单并生成 V2，不是废弃数据。
- 三份 P04B（林晚、周砚、驻岛站）在当前 EntityRegistry 已有相应实体的情况下重复调用，输出没有形成新增注册提交。V1.4.1 的 preflight 已在这三份原始输入包上重放，三份均得到 `SKIP/ENTITY_ALREADY_REGISTERED`。

### 3.2 冲突、资产和事件

- P09 生成7条冲突候选，全部进入 P10 分类。
- P10 结果：1条互斥错误进入 P11；1条 `NO_MATERIAL_CONFLICT` 合法终止；5条张力候选进入 P12。
- P12 产生的 **5条 StoryAsset 全部被 P13 的 `asset_refs` 引用**。本轮不存在“5条资产只用了3条”的情况；测试包中某段文字报告写3条，与 `outputs/P13_chapter-6.json` 实际5条 `asset_refs` 不一致，应以 JSON 输出为准。
- P13 的5条资产透镜被后续事件/章节规划读取。
- P14A 按“一条资产一条事件”产出5个 EventCandidate；5条均进入 P14B/P17A 检查，因此它们不是无引用孤儿。
- 其中2条因 `PENDING_EVIDENCE` 没有进入排序，3条进入 P14C；P14C 因状态节点重复所有权、重复收存动作和依赖循环，无法形成有效总序。
- 因此：**5个事件候选都被审查使用，但0个成为已批准、可冻结的章节事件序列。** 这属于“候选未晋级”，不是“输出文件被删除”。

### 3.3 Writer 与审计

- P17C V1 被 V2 替代；V1 作为前置依赖诊断保留。
- P17C 最终仍为 BLOCKED。
- P18 在 BLOCKED 条件下被强制生成一份诊断草稿，并被 P19 系列审计读取；它不是合格的生产章节。
- P19F 没有批准 VoiceCard，不能评估与人物语言身份卡的一致性；报告中 `UNKNOWN` 不能解释为 PASS，因此该调用属于可避免成本。
- P19D 的3份输出输入的是事件设计数据，不是已渲染正文；它们只能作为设计层审计，不能宣称完成了正文因果审计。
- 最终正式批准章节数为 **0**。

## 4. 为什么会产生最终没有采用的事件候选？

主要不是模型“乱写”，而是工作流把多条资产机械地一一映射成事件：

1. 五条资产指向同一章、同一档案室、相近行动者和相同调阅/登记程序。
2. P14A 按一资产一事件，产出四个高度相似的 `push_event` 加一个相邻 `character_moment`。
3. 多个事件重复声称同一 BASE 变化节点，出现节点所有权冲突。
4. 事件文本又对“日志重新收存”“交换提议”“边界声明”产生互相依赖，形成先后循环。
5. P14C 因此正确拒绝给出伪造的总顺序。

这是事件机会聚类、组合筛选和状态节点唯一归属缺失造成的流程成本。V1.4.0 已对此增加 P12B、P13B、P14C0，但必须用下一轮运行结果验证修复效果。

## 5. 可避免调用与应保留的“未采用”结果

### 明确可避免（5次）

- 3次 P04B：输入包已显示候选实体存在于 `current_entity_registry.entities`，应由宿主预检直接 `SKIP_ALREADY_REGISTERED`。
- 1次 P05C：`language_samples=[]` 且状态 `EMPTY_BY_FIXTURE`，应在调用前 `SKIP_NO_LANGUAGE_SAMPLE`，不生成空 VoiceCard。
- 1次 P19F：无已批准/冻结 VoiceCard，应在调用前 `SKIP/NO_APPROVED_VOICE_CARD`，不开展正式声纹保真审计。

### 不应简单删除（4类）

- 1次 P10 `NO_MATERIAL_CONFLICT`：正确终止判断，价值在于明确无需制造故事资产。
- 1次 P11 `applied=false`：保留为未批准提案，防止静默修改来源变量线。
- 1次 P17C V1：被 V2 替代，但对定位缺少 WC 全文等依赖有诊断价值。
- 5条 P14A 事件候选：虽然最终未晋级，但用于可行性审查和暴露重复节点/循环问题；真正应优化的是上游事件机会聚类，不能把失败候选直接算作无用文件。

P19F 的缺失基线不是可以忽略的诊断附加项，而是正式审计的前置条件不成立：本次应由 preflight 跳过。

## 6. 输入包效率：提示词短了，但输入还很大

| 指标 | 结果 |
|---|---:|
| 输入包数量 | 73 |
| 输入包总字节数 | 4,536,162（4.326 MiB） |
| 超过200 KiB需复核 | 4份 |
| 超过300 KiB需例外审批 | 3份 |
| 重复 JSON 子树组 | 76组 |

最大输入包：

- P18 输入包：504.1 KiB；
- P17C 输入包：442.4 KiB；
- 独立 WRITER_PACK：414.6 KiB；
- P14C 输入包：228.6 KiB。

### 明确重复的上下文

- 完整 `writer_input_pack`（约340 KiB）被完整嵌入 P17C、P18，并单独保存成 WRITER_PACK，共3份。
- `approved_events_with_checks`（约169.6 KiB）也重复嵌入上述3处。
- P18 顶层单独放了一份 `chapter_outline`，同时 Writer Pack 内已有同一大纲（约37.3 KiB）。
- P17C 只需要检查依赖闭包、审批状态、版本和 hash，不需要加载完整 Writer Pack，更不需要加载全部事件正文。
- P19D 每次审一个事件时，只需要 focal event 和必要前后事件/状态切片，不应把整章所有事件复制进来。

检测到76组重复子树，但它们存在嵌套，不能把每组重复字节简单相加当成可节省总量。字节量只是 token 成本的代理指标；实际 token 应使用目标模型 tokenizer 计算。

### 不是所有重复都应该删除

独立会话意味着 P07A、P07B、P07C 可能都需要各自读取同一条 BASE 线的不同投影。这是为了隔离上下文，不应为了减少字节把它们强行合并成一个审计任务。

正确做法是：每个任务只装入它需要的 BASE 节点和字段投影；P09 等确实需要完整双线扫描的任务，才加载完整两条变量线。

## 7. V1.4.1 修复方向

1. 增加确定性 `preflight_task_call.py`：已注册实体、空语言样本、无批准 VoiceCard、无机制调用等情形在 LLM 调用前直接 SKIP/NOT_APPLICABLE；其他未覆盖任务返回 `NEEDS_HOST_CHECK`，不得误当自动 READY。
2. `TASK_LIFECYCLE_REGISTRY.csv` 为每个任务明确消费者、跳过条件、终态处理和 preflight 规则。
3. 加强 Writer Input Pack 去重：P17C 只接收依赖闭包摘要与批准清单，不接收完整 Writer Pack；P18 只加载一次完整 Writer Pack，不再重复顶层 outline。
4. 对事件候选、资产、变量线节点分别记录 `PROPOSED/SELECTED/MERGED/DEFERRED/REJECTED/APPROVED` 生命周期；被拒绝的输出保留审计理由，不删除。
5. 增加数据消费追踪和输入包重复扫描工具。精确/领域 ID 引用只证明可追踪引用，不声称语义采用。
6. 生产 Writer 必须由 P17C=READY 作为硬门禁；BLOCKED 时只能在明确授权下运行诊断渲染。

## 8. 边界

本次只根据上传测试包的运行卡、输入包、输出 JSON、冻结清单和报告统计。引用追踪不能完全判断模型内部是否真正使用了数据；本轮没有正式批准章节，故无法统计变量线/资产最终进入“出版正文”的真实比例，只能统计进入后续任务、诊断和门禁的可追踪消费。


Preflight 重放证据见 `TR-20261104_MULTILINE_preflight_replay.json`。它对历史输入包执行确定性预检，不是重新运行原始 LLM 调用。
