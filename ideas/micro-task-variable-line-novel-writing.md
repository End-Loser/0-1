## 核心主张

长篇小说生成可以拆成“一次模型调用只执行一个微任务”的提示词流水线，并以完整的变量线（entity × dimension 的时间轨迹）作为 canon 上下文；生成、审计、修订、批准与冻结分离；未解决的矛盾不直接交给 Writer。这样的流程可能降低长上下文漂移、事件同质化和可避免调用，并让每一步可追踪。

**范围限定**：这是关于流程可审计性与工程可行性的主张，不是“文学质量已提升”或“整本书可以自动生成”的结论。

## 背景与动机

长篇小说写作中常见的问题包括：上下文越来越长导致设定漂移；多个资产被机械地变成同质事件；冲突没有解释就被当作事实；生成、审计和修订混在一次调用里，无法追踪哪份输出被下游使用。

CVNS R-06.2 的思路是把这些环节拆开：

- 一次调用一个自然任务，独立会话、独立输入包、独立输出；
- 用变量线记录人物 / 世界状态的时间轨迹；
- 冲突先解释、再批准、再资产化；未批准的解释不进入 Writer；
- 资产按 SETUP / REVEAL / PAYOFF 阶段部署；事件去重并绑定唯一节点；
- 静态工具与测试验证结构、预算、契约和回归。

## 事实、推断与猜测

### 事实（据项目归档）

- v1.7.0 包包含 83 个 `TASK_REGISTRY.csv` 任务行、84 个提示词文件、45 个工具、43 个测试，以及 schemas、workflows、case_studies。
- V1.4.1 历史归档的一次小规模实测：73 份模型输出，60 份（82.2%）有下游 ID 引用；5 份（6.8%）可避免调用；正式批准章节 0，只有一份约 4,628 汉字的诊断草稿。
- 成本记录：子代理 ¥23.27 + 主会话 ¥7.34 = API 合计 ¥30.61；不是完整小说生成成本。
- 项目 README 明确说明：Skill 是提示词与宿主流程规范，不是原 R-06.2 Python 工程源码替代。

### 推断

- 结构化微任务与变量线有利于追踪、复用和减少重复调用。
- 但“结构正确”不等于“故事好看”；当前证据不足以证明文学质量提升。

### 猜测 / 待验证

- 在更多样本和对照下，流程可能降低 canon 矛盾率与可避免调用，同时成本可能上升。
- 30 章压力测试在 v1.7.0 中已做提示词升级，但 clean 包没有给出完整的 v1.7.0 文学质量对照。

## 支持证据与反例

### 支持性证据

- 项目把生成、审计、修订、批准、冻结拆成独立步骤，并提供了任务注册表、输出契约、schema 与静态验证工具。
- 历史实测中 60/73 输出有下游引用，说明流程至少能追踪“哪些输出被使用”。
- 5 次可避免调用被识别，说明 preflight / 消费追踪有实际作用。

### 反例与限制

- 历史实测正式批准章节为 0；5 个事件候选都未晋级为可冻结的章节事件序列。
- 静态测试只验证结构与预算，不验证人物、因果、文风或读者体验。
- 输入包仍然很大；项目自己报告了重复子树和 150 / 200 / 300 KiB 阈值。
- 需要宿主实现权限、会话隔离、审批与冻结；没有宿主时无法完成整条流程。

## 验证或证伪方法

建议做同任务、同模型、同预算的对照实验：

1. 同一大纲、同一模型、同一预算，分别使用本流程与“简单长提示 + 直接写作”基线。
2. 预注册指标：canon 矛盾率、事件同质化比例、可避免调用数、总成本、人工审读评分、批准章节数。
3. 记录每次调用的输入包大小、输出消费状态和失败分支。
4. 若本流程在矛盾率 / 同质化 / 成本上没有可重复优势，或质量明显下降，应缩小主张范围或修正流程。
5. 用至少两部不同题材、不同规模的小说复现，避免单样本结论。

## 风险与边界

1. **模型依赖**：实际模型、tokenizer、费用和输出质量随 provider / model 变化。
2. **流程复杂**：提示词、schema、宿主和审批链增加工程成本；小项目可能不划算。
3. **文学质量**：结构验证不等于文学判断；当前没有完整整书结果。
4. **版权 / 隐私**：本归档不包含测试小说正文、样章或修订候选；设计书/代码归档不替代真实样本的版权审查。第三方引用需核对许可。
5. **误用**：不要用于侵权、冒充、误导或规避平台规则的内容生成。
6. **成本**：历史记录只是一次小规模诊断的费用，不是整书预算。
